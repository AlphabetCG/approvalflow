## Decisions

Proposed here; accepted in the review of this contract (recorded in `docs/srs.md` §7).

| ID | Decision | Why |
|---|---|---|
| D-18 | A draft is validated with **the same rules as a submit** (F-02: D-03 categories, D-04 title 1–200 and description 1–2000 after trimming, BR-04 amount 0.01–100,000 with at most 2 decimals). There are no half-filled drafts. | One validator for create, edit and submit. The database CHECK constraints (BR-04) stay as they are and no column becomes nullable except the two in D-19. F-06 edits a `RETURNED` request with the same endpoint, and a returned request must stay complete. |
| D-19 | A draft has **no reviewer and no `submittedAt`**. The reviewer is assigned by D-01 when the draft is **submitted**, and `submittedAt` is set then. | The reviewer must not see or be counted for a request that is not in their queue. Round-robin (D-01) keeps counting submitted requests only. |
| D-20 | Three endpoints: `POST /api/requests/drafts` (create), `PATCH /api/requests/:id` (edit, the body carries all four fields), `POST /api/requests/:id/submit` (`DRAFT → SUBMITTED`). Edit is allowed only in `DRAFT` (BR-05); F-06 adds `RETURNED` to the same guard. | `POST /api/requests` keeps its F-02 meaning (submit at once), so Sprint 1 clients and tests do not change. The client always sends the whole form, so the full body avoids merging a partial update with stored values. |
| D-21 | Only the **requester** may read, edit or submit their draft. Anyone else, including every reviewer, gets the same 404 as an unknown id (D-10). Edit and submit look the request up **by id and requester** in the query, so another user's request is never loaded. | Same rule and the same technique as D-10 and D-13. A draft is private until it is submitted. |
| D-22 | History: creating a draft writes one row `CREATE_DRAFT`, `null → DRAFT`; submitting it writes `SUBMIT`, `DRAFT → SUBMITTED`. **Editing writes no history row**, because the status does not change (FR-07 records state changes; BR-06 keeps rows append-only). | The History shows when a request was started and when it entered review, without a row per keystroke-save. F-06 decides separately whether editing a `RETURNED` request is recorded. |
| D-23 | My requests (revises the order of D-11): **drafts first**, newest created first, then all other requests by `submittedAt`, newest first. A draft shows "Not submitted" and no reviewer. | A draft has no `submittedAt`, so it needs its own place, and unfinished work belongs at the top. |

**Out of scope for F-05:** deleting a draft (no delete in Sprint 2; a draft can stay a draft), attachments, autosave, editing a `SUBMITTED` request (never allowed, BR-05), the `RETURNED` status (F-06).

## Behavior and workflow

1. **Save draft.** On "New request" the user fills in the form and clicks **Save draft**. The client validates the form exactly as for submit (F-02, AC-02-9). The API validates again, stores the request with status `DRAFT`, no reviewer, no `submittedAt`, and writes the `CREATE_DRAFT` history row, in one transaction. The client opens the draft's detail page.
2. **Edit.** On the detail page of their own draft the requester clicks **Edit**. The edit page shows the form filled with the stored values. **Save changes** validates and sends `PATCH`. The status stays `DRAFT`; no history row is written.
3. **Submit.** On the detail page of their own draft the requester clicks **Submit request**. In one transaction the API checks the status is still `DRAFT`, assigns a reviewer (D-01, never the requester), sets `submittedAt = now`, changes the status to `SUBMITTED` and writes the `SUBMIT` history row. From now on the request behaves exactly like a Sprint 1 submitted request (F-03, F-04, CR-01).

### State machine (additions to System-Level SDS §3)

| From | Action | To | Who |
|---|---|---|---|
| – | create draft | `DRAFT` | requester |
| `DRAFT` | edit | `DRAFT` (no history row) | requester |
| `DRAFT` | submit | `SUBMITTED` | requester |

Any other transition from `DRAFT` (approve, reject, a second submit after the first) is rejected. `decide()` never matches a draft for a reviewer, because a draft has no reviewer (D-19); a reviewer who is the draft's own requester gets 403 from F-04 check 5.

### Check order

`POST /api/requests/drafts`: 401 → 400 body (F-02 validation) → 201.

`PATCH /api/requests/:id`:

| # | Check | Response |
|---|---|---|
| 1 | No session (NFR-01) | 401 `UNAUTHENTICATED` |
| 2 | Body fails F-02 validation | 400 `VALIDATION_ERROR` with `details` (same shape as F-02) |
| 3 | No request with this id **whose requester is the caller** | 404 `NOT_FOUND`, "Request not found" (same body as an unknown id) |
| 4 | Status is not `DRAFT` (BR-05; F-06 adds `RETURNED`) | 409 `CONFLICT`, "Only a draft can be edited" |
| 5 | The status changed between the check and the update (a submit won the race, BR-07) | 409 `CONFLICT`, "Only a draft can be edited" |

`POST /api/requests/:id/submit`:

| # | Check | Response |
|---|---|---|
| 1 | No session | 401 |
| 2 | No request with this id whose requester is the caller | 404, same body as an unknown id |
| 3 | Status is not `DRAFT` | 409 `CONFLICT`, "This request is already SUBMITTED" / `APPROVED` / `REJECTED` |
| 4 | No eligible reviewer in the requester's department (D-01) | 409 `CONFLICT`, "No reviewer is available in your department"; the request stays `DRAFT` |
| 5 | Another submit of the same draft won the race (BR-07) | 409 `CONFLICT`, "This request is already SUBMITTED" |

In every failure case nothing changes: no field, status or history row. The status update is conditional (`WHERE status = 'DRAFT'`), so of two simultaneous submits only one writes a `SUBMIT` row, as in F-04 (BR-07).

## Permissions

| Operation | Requester (own) | Other requester | Reviewer (not the requester) |
|---|---|---|---|
| Create a draft | ✓ (any signed-in `REQUESTER` or `REVIEWER`, like F-02) | – | – |
| Read a draft (`GET /api/requests/:id`) | ✓ | 404 | 404 (a draft has no reviewer, so D-10 already hides it) |
| See a draft in My requests | ✓ | – | – |
| See a draft in the review queue | – | – | never (the queue lists `SUBMITTED` only, D-15) |
| Edit / submit a draft | ✓ | 404 | 404 |

Hiding the buttons is not the protection: the API scopes the lookup to the requester (D-21).

## API

| Method | Path | Request | Success | Errors |
|---|---|---|---|---|
| POST | `/api/requests/drafts` | `{ "title", "category", "amount", "description" }` (as F-02) | 201, request body below with `status: "DRAFT"` | 400, 401 |
| PATCH | `/api/requests/:id` | the same four fields, all required | 200, request body | 400, 401, 404, 409 |
| POST | `/api/requests/:id/submit` | `{}` (any body is ignored) | 200, request body with `status: "SUBMITTED"`, `reviewer`, `submittedAt` | 401, 404, 409 |
| GET | `/api/requests/:id`, `/api/requests/mine` | unchanged (F-03) | `reviewer` and `submittedAt` may now be `null` (drafts) | unchanged |

Request body returned by the three new endpoints (the F-02 shape; `reviewer` and `submittedAt` are `null` for a draft):

```json
{
  "id": "<id>",
  "title": "Conference travel",
  "category": "TRAVEL",
  "amount": "1500.00",
  "description": "Train tickets to the conference",
  "status": "DRAFT",
  "submittedAt": null,
  "requester": { "id": "<id>", "email": "requester@example.com" },
  "reviewer": null
}
```

Fields `status`, `reviewerId`, `requesterId`, `submittedAt` in any body are ignored (F-02 AC-02-8 applies to all three endpoints). A 400 has the F-02 `details` shape.

## Data

Two migrations, because PostgreSQL cannot use a new enum value inside the transaction that adds it:

1. `add_draft_status`: `ALTER TYPE "RequestStatus" ADD VALUE 'DRAFT'`; `ALTER TYPE "HistoryAction" ADD VALUE 'CREATE_DRAFT'`.
2. `drafts_without_reviewer`:
   - `Request.reviewerId` and `Request.submittedAt` become nullable (`submittedAt` keeps no default; the code sets it on submit).
   - New `Request.createdAt TIMESTAMP(3) NOT NULL DEFAULT CURRENT_TIMESTAMP`; existing rows are backfilled with `createdAt = submittedAt`.
   - CHECK added by hand: `CHECK (("status" = 'DRAFT') = ("reviewerId" IS NULL AND "submittedAt" IS NULL))`: a draft has neither, every other request has both.

Existing constraints stay: `amount > 0 AND amount <= 100000` (BR-04) and `requesterId <> reviewerId` (a NULL reviewer passes a CHECK). Existing rows are all `SUBMITTED`, `APPROVED` or `REJECTED` with a reviewer and `submittedAt`, so the new CHECK holds for them. No seed change.

**Effects on existing code (to verify in the implementation):**
- F-02 `submitRequest`: "last assigned" filters on `reviewer.department`, so drafts (no reviewer) are never counted. The new submit reuses the same assignment code; it is moved into a shared function, not copied.
- F-03 `read.ts`: types allow `reviewer: null` and `submittedAt: null`; the `/mine` order follows D-23.
- F-04 `decide()` and the queue: no change. A draft cannot match a reviewer (no reviewer), and the queue filters on `SUBMITTED`.
- CR-01 (BR-08): no change. It applies when the submitted request is approved.
- Client `types.ts`, My requests and the detail page: show "Not assigned yet" / "Not submitted" for `null`.

## Acceptance criteria

| ID | Given / When / Then |
|---|---|
| AC-05-1 | Given a signed-in requester (or reviewer) and valid data, when they save a draft, then the response is 201 with status `DRAFT`, `reviewer: null`, `submittedAt: null`, and one history row records `CREATE_DRAFT`, `null → DRAFT`, by them. |
| AC-05-2 | Given invalid data (any F-02 rule), when saving a draft or saving an edit, then the response is 400 with `details` and nothing is stored or changed. |
| AC-05-3 | Given the requester's own draft, when they save an edit with valid data, then the response is 200 with the new values, the status is still `DRAFT`, and no history row is added. |
| AC-05-4 | Given the requester's own request in `SUBMITTED`, `APPROVED` or `REJECTED`, when they try to edit it, then the response is 409 and nothing changes (BR-05). |
| AC-05-5 | Given a draft, when another requester, a reviewer of the same department, or anyone not its requester reads, edits or submits it, then the response is 404 with the same body as an unknown id, and nothing changes. |
| AC-05-6 | Given the requester's own draft, when they submit it, then the response is 200, the status is `SUBMITTED`, a reviewer is assigned by D-01 (never the requester), `submittedAt` is set, a `SUBMIT` history row `DRAFT → SUBMITTED` is added, and the request appears in that reviewer's queue. |
| AC-05-7 | Given drafts of several users, when any reviewer opens the review queue, then no draft is listed. |
| AC-05-8 | Given a draft whose department has no eligible reviewer, when it is submitted, then the response is 409 and it stays `DRAFT` with no new history row. |
| AC-05-9 | Given a request that is no longer a draft, when it is submitted again, then the response is 409; given two simultaneous submits of one draft, then exactly one succeeds and exactly one `SUBMIT` row is stored. |
| AC-05-10 | Given a requester with drafts and submitted requests, when they open My requests, then the drafts are listed first (newest created first), then the others by `submittedAt`, newest first. |
| AC-05-11 | Given no session, when any of the three new endpoints is called, then the response is 401 and nothing is stored. |
| AC-05-12 | Given the UI: Save draft with invalid input shows the field messages and makes no call; the requester's draft shows Edit and Submit request, nobody else sees them; the edit page is filled with the stored values; a 409 shows its message; after submit the page shows the new status and reviewer without a reload. |
