## Decisions

Proposed here; accepted in the review of this contract (recorded in `docs/srs.md` §7).

| ID | Decision | Why |
|---|---|---|
| D-24 | Filters are **query parameters on the two existing lists**: `GET /api/requests/mine?status=&category=&from=&to=` and `GET /api/reviews/queue?category=&from=&to=`. No new endpoint, no search text in Sprint 2. Without parameters both lists answer exactly as before (F-03, F-04). | FR-11 names status, category and date. Reusing the lists keeps their access rule and their `{ "requests": [...] }` body (D-12), so the clients only add a query string. |
| D-25 | `status` is one value of the `RequestStatus` enum, `category` one value of D-03. Values are **upper case and exact**. The validator reads the allowed statuses from the Prisma enum, so `DRAFT` (F-05) and `RETURNED` (F-06) are accepted as soon as their migrations exist. The queue accepts **no** `status` (it lists `SUBMITTED` only, D-15): a `status` there is a 400. | One source of truth for the statuses. A silent ignore of `status` on the queue would let a client believe it filtered. |
| D-26 | `from` / `to` are calendar dates `YYYY-MM-DD` in **Asia/Bangkok** (UTC+7, no daylight saving), both **inclusive**, on `submittedAt`. `from` means `submittedAt >= from 00:00+07:00`; `to` means `submittedAt < (to + 1 day) 00:00+07:00`. `from` after `to` is a 400, checked only when both are valid dates (one mistake, one error). A request resubmitted after F-06 keeps its first `submittedAt`, so the filter uses the first submit date. | The department works in Bangkok time and the server image runs with `TZ=Asia/Bangkok`. Converting with a fixed offset gives exact boundaries in tests, whatever time zone the browser or CI uses. |
| D-27 | A request without `submittedAt` (an F-05 draft) **never matches a date filter**. With only `status`/`category`, drafts are filtered like any other request. | A draft has no submit date (D-19). Matching it on `createdAt` would mix two meanings of "date" in one filter. |
| D-28 | Validation answers **400 `VALIDATION_ERROR`** with `details: [{ field, message }]` per bad parameter (the F-02 shape). An empty value (`?status=`) is the same as no filter. A parameter given twice (`?status=A&status=B`) is a 400. Unknown parameters are ignored. | Same error shape the clients already show. Empty values come from a form with "All" selected. Repeated values would need OR semantics, which FR-11 does not ask for. |

**Out of scope for F-08:** free-text search, several statuses at once, sorting options, paging (D-12 stays: no paging), filtering on `createdAt` or on decision date, a list of requests a reviewer has already decided (that is the F-09 summary).

## Behavior and workflow

1. The requester opens **My requests**. A filter bar above the table has Status (All + the statuses), Category (All + D-03), From and To (date inputs), and the buttons **Apply** and **Clear**.
2. **Apply** checks on the client that `from` is not after `to` (otherwise a message and no call), then puts the non-empty filters in the page URL (`/requests?status=APPROVED&from=2026-11-01`) and loads `/api/requests/mine` with the same query string. Reload, back and a shared link keep the filters, because the page reads them from its URL.
3. The API validates the parameters (D-25, D-26, D-28), adds them to the query **together with** the requester condition, and answers the matching requests in the unchanged order (D-11 / D-23).
4. An empty result shows "No requests match these filters." with a **Clear** link, not the "You have not submitted any requests yet" text of F-03.
5. The **Review queue** has the same bar without Status, and calls `/api/reviews/queue` with `category`, `from`, `to`.

### Check order

Both endpoints:

| # | Check | Response |
|---|---|---|
| 1 | No session (NFR-01) | 401 `UNAUTHENTICATED` |
| 2 | Queue only: role is not `REVIEWER` | 403 `FORBIDDEN` (unchanged, F-04) |
| 3 | A parameter is repeated, `status` not in the enum (or given to the queue), `category` not in D-03, a date not `YYYY-MM-DD` or not a real date (`2026-02-30`), or `from` after `to` | 400 `VALIDATION_ERROR`, one `details` entry per bad field |
| 4 | Valid | 200 `{ "requests": [...] }`, possibly empty |

Access is never part of the filter: the `where` clause is always `requesterId = me` (mine) or `reviewerId = me AND status = 'SUBMITTED'` (queue), **AND** the filters. A filter can only narrow a list, never widen it.

### Validation messages (`details[].message`)

| Field | Case | Message |
|---|---|---|
| `status` | not a known status | `Status must be one of: <values>` |
| `status` | sent to the queue | `The review queue cannot be filtered by status` |
| `category` | not in D-03 | `Category must be one of: TRAVEL, SUPPLIES, EQUIPMENT, TRAINING, OTHER` |
| `from` / `to` | not `YYYY-MM-DD` or not a real date | `From must be a date (YYYY-MM-DD)` / `To must be a date (YYYY-MM-DD)` |
| `to` | `from` after `to` (both valid dates) | `To must not be before From` |
| any | given twice | `<Field> can be given only once` |

## Permissions

| Operation | Requester | Reviewer | No session |
|---|---|---|---|
| Filter My requests (own requests only) | ✓ | ✓ (their own submitted requests, as F-03) | 401 |
| Filter the Review queue (assigned `SUBMITTED` only) | 403 | ✓ | 401 |

No filter value can name another user: there is no `requesterId` / `reviewerId` parameter, and such parameters are ignored (D-28).

## UI

| Place | Behavior |
|---|---|
| My requests, filter bar | Status select (All, then `REQUEST_STATUSES`, one new client constant in `requests/types.ts` that F-05/F-06 extend with `DRAFT`/`RETURNED`; the client has no status list today), Category select (All + D-03 labels from `format.ts`), From, To (`<input type="date">`), **Apply**, **Clear**. The controls show the values from the URL when the page opens. |
| Apply | `from` after `to`: "To must not be before From" beside To, no API call. Otherwise the URL query is replaced with the non-empty values and the list reloads ("Loading…"). |
| Clear | Removes all filters from the URL and reloads the unfiltered list. |
| Result | The table as in F-03 (D-23 order once F-05 is in). Above it: "Results: N" when a filter is active. Empty with filters: "No requests match these filters." and a Clear link. Empty without filters: unchanged F-03 text. |
| 400 from the API (e.g. a hand-edited URL) | The `details` messages in an alert above the table; the controls keep the values; no table. |
| Review queue, filter bar | The same without Status. Empty with filters: "No requests match these filters."; without filters: unchanged "Nothing to review." |

Note: the Submitted column (`formatDateTime`) uses the browser's time zone, the filter uses Bangkok days. A browser outside UTC+7 can show a time that looks outside the chosen range. Users of the demo are in Bangkok, so F-08 leaves `format.ts` unchanged (recorded as technical debt).

## API

| Method | Path | Query | Success | Errors |
|---|---|---|---|---|
| GET | `/api/requests/mine` | `status`, `category`, `from`, `to` (all optional) | 200 `{ "requests": [...] }`, body items unchanged (F-03) | 400, 401 |
| GET | `/api/reviews/queue` | `category`, `from`, `to` (all optional) | 200 `{ "requests": [...] }`, items unchanged (F-04) | 400, 401, 403 |

Example: `GET /api/requests/mine?status=APPROVED&from=2026-11-01&to=2026-11-30`

400 example:

```json
{
  "error": "VALIDATION_ERROR",
  "message": "Status must be one of: SUBMITTED, APPROVED, REJECTED; To must not be before From",
  "details": [
    { "field": "status", "message": "Status must be one of: SUBMITTED, APPROVED, REJECTED" },
    { "field": "to", "message": "To must not be before From" }
  ]
}
```

(The status list in the message is the enum at run time; with F-05/F-06 it also names `DRAFT` / `RETURNED`.)

## Data

No migration and no schema change. The filters use existing columns (`status`, `category`, `submittedAt`) on rows already narrowed by `requesterId` (index `@@index([requesterId])`) or `reviewerId, status` (index `@@index([reviewerId, status])`). One user has at most a few hundred requests, so no new index is needed in Sprint 2.

**Effects on existing code (to verify in the implementation):**
- New `server/src/requests/filters.ts`: `parseRequestFilters(query, { allowStatus })` → `{ ok, value: { status?, category?, submittedFrom?, submittedBefore? } }` or `{ ok: false, errors }`; the Bangkok-day → UTC conversion lives here only.
- `read.ts` `listMyRequests(userId, filters?)` and `decide.ts` `listQueue(reviewerId, filters?)`: optional second argument, merged into the existing `where` with AND. The order clauses do not change.
- `routes/requests.ts` `/mine` and `routes/reviews.ts` `/queue`: parse, 400 on errors, pass the filters.
- Client: `MyRequestsPage.tsx` and `ReviewQueuePage.tsx` read `useSearchParams()`; a shared `FilterBar` component. The F-03/F-04 component tests that render the pages without a query keep passing (guards).
- F-05 conflict point: F-05 changes `listMyRequests`' `orderBy` (D-23). F-08 only adds to `where`, so the two changes touch different lines; whichever merges second rebases.

## Acceptance criteria

| ID | Given / When / Then |
|---|---|
| AC-08-1 | Given a requester with requests in several statuses, when they filter My requests by one status, then only their requests with that status are returned, in the F-03 order. |
| AC-08-2 | Given requests in several categories, when filtering by a category (mine or queue), then only that category is returned. |
| AC-08-3 | Given requests submitted at 2026-11-09 23:59:59.999 +07:00, 2026-11-10 00:00:00.000 +07:00, 2026-11-20 23:59:59.999 +07:00 and 2026-11-21 00:00:00.000 +07:00, when filtering `from=2026-11-10&to=2026-11-20`, then exactly the middle two are returned (inclusive Bangkok days, D-26). `from` alone and `to` alone are open on the other side. |
| AC-08-4 | Given several filters, then they combine with AND. Given no filter or only empty values, then the response equals the unfiltered list of F-03 / F-04. |
| AC-08-5 | Given an invalid value (unknown status or category, a malformed or impossible date, `from` after `to`, a repeated parameter), then the response is 400 with one `details` entry per bad field. |
| AC-08-6 | Given another user's request that would match the filters, then it is never returned, by any filter combination, on either list (NFR-03). Parameters such as `requesterId` or `reviewerId` are ignored. |
| AC-08-7 | Given the queue, when called with `category`/`from`/`to`, then only assigned `SUBMITTED` requests matching them are returned, oldest first; when called with `status`, then 400. |
| AC-08-8 | Given an F-05 draft (no `submittedAt`), then it is returned by `status=DRAFT` and by `category`, and never when `from` or `to` is set (D-27). (Runs once F-05 is merged.) |
| AC-08-9 | Given no session, then both endpoints answer 401 with or without filters; a requester calling the queue with filters gets 403. |
| AC-08-10 | Given the UI: the filter bar shows the URL's values on load; Apply with From after To shows the message and makes no call; Apply puts the filters in the URL and calls the API with the same query; Clear removes them; an empty filtered result shows "No requests match these filters."; a 400 shows its messages. |
