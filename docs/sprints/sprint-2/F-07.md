## Decisions

Proposed here; accepted in the review of this contract (recorded in `docs/srs.md` §7). D-02 was agreed in the team discussion of 2026-11-28.

| ID | Decision | Why |
|---|---|---|
| D-02 | Second-stage threshold: a request **above 50,000.00 THB** needs two approvals. At or below 50,000.00 one approval is final, as in Sprint 1. Compared as Decimal (`amount.greaterThan(50000)`), like BR-08. | Well above BR-08's 20,000.00, so the two rules do not collide, and below the BR-04 maximum of 100,000.00, so the stage is reachable. |
| D-34 | New status **`SECOND_REVIEW`** between `SUBMITTED` and `APPROVED`. A stage-1 approval of a request above D-02 moves `SUBMITTED → SECOND_REVIEW`; the stage-2 approval moves `SECOND_REVIEW → APPROVED`. A reject at either stage ends it (`→ REJECTED`). | A status (not a separate stage number) keeps one state machine (BR-02), makes the stage visible in lists and filters (F-08) and reuses the conditional update of BR-07. |
| D-35 | New nullable column **`secondReviewerId`**. It is set in the same transaction as the stage-1 approval, by round-robin (D-01) among the requester's department reviewers **excluding the requester and the stage-1 reviewer**, starting after the department's last second-stage reviewer. `reviewerId` keeps the stage-1 reviewer. | Both reviewers stay on the request, so both keep read access (D-10) and history shows who approved at each stage. Round-robin spreads the load the same way as stage 1. |
| D-36 | If nobody is eligible for stage 2, the stage-1 approval is **refused with 409** `No second reviewer is available in this department`, and nothing changes (status `SUBMITTED`, no history row). The stage-1 reviewer can still reject. | Same rule as D-01 when nobody can be assigned. Storing a half-done approval with no one to finish it would leave the request stuck. |
| D-37 | Who acts: in `SUBMITTED` the stage-1 reviewer (`reviewerId`), in `SECOND_REVIEW` only the second reviewer (`secondReviewerId`). The stage-1 reviewer acting in `SECOND_REVIEW` gets **403** `The second approval must come from another reviewer`. Stage 2 has **approve and reject only**: return (F-06) in `SECOND_REVIEW` is a 409. | BR-01 in spirit: one person cannot approve twice. 403 (not 404) because that reviewer may read the request. Returning after one approval would throw that approval away; F-06 keeps return at stage 1. |
| D-38 | History uses the existing actions: the stage-1 row is `APPROVE` `SUBMITTED → SECOND_REVIEW`, the stage-2 row `APPROVE` or `REJECT` from `SECOND_REVIEW`. No new history action. BR-08 applies at **both** stages (every request above 50,000 is above 20,000). | Status columns already tell the stage. F-09 counts each `APPROVE` row as one decision of its actor. |

**Out of scope for F-07:** more than two stages, choosing the second reviewer by hand, reassigning a reviewer, admin overrides, a second stage across departments.

## Behavior and workflow

1. The stage-1 reviewer opens a `SUBMITTED` request of 50,000.01 THB or more. The detail shows "Needs two approvals (above 50,000 THB)". They approve with a comment (BR-08).
2. The API checks access and state (as F-04), BR-08, then D-02. Above D-02 it picks the second reviewer (D-35), sets `status = SECOND_REVIEW` and `secondReviewerId` with a conditional update, and writes one history row, all in one transaction. With nobody eligible: 409 (D-36), nothing stored.
3. The page shows "Approved at stage 1. Sent to <second reviewer> for the second approval." The request leaves the stage-1 reviewer's queue and appears in the second reviewer's queue, marked "Stage 2".
4. The second reviewer approves (comment required, BR-08) → `APPROVED`, or rejects (reason, BR-03) → `REJECTED`.
5. The requester sees `SECOND_REVIEW` in My requests and both reviewers on the detail page. At or below 50,000.00 nothing changes from Sprint 1.

### State machine (adds to System-SDS §3)

| From | Action | Condition | To | Who |
|---|---|---|---|---|
| SUBMITTED | approve | amount ≤ 50,000.00 | APPROVED | stage-1 reviewer |
| SUBMITTED | approve | amount > 50,000.00 and a second reviewer exists | SECOND_REVIEW | stage-1 reviewer |
| SUBMITTED | reject | – | REJECTED | stage-1 reviewer |
| SECOND_REVIEW | approve | – | APPROVED | second reviewer |
| SECOND_REVIEW | reject | – | REJECTED | second reviewer |

### Check order (approve and reject; replaces F-04 v4 rows 4–8)

| # | Check | Response |
|---|---|---|
| 1–3 | Session, role, body (unchanged F-04) | 401 / 403 / 400 |
| 4 | Caller is not the requester, the stage-1 or the second reviewer (D-13, D-10) | 404 `Request not found` |
| 5 | Caller is the requester (BR-01) | 403 `You cannot decide on your own request` |
| 6 | Status allows no decision (`APPROVED`, `REJECTED`, …) | 409 `This request is already <STATUS>` |
| 7 | `SECOND_REVIEW` and the caller is the stage-1 reviewer (D-37); `SUBMITTED` and the caller is only the second reviewer cannot happen (set in stage 1) | 403 `The second approval must come from another reviewer` |
| 8 | Approve, amount > 20,000.00, comment < 10 characters (BR-08) | 400 (unchanged) |
| 9 | Stage-1 approve above D-02 and nobody eligible (D-36) | 409 `No second reviewer is available in this department` |
| 10 | Conditional update finds the status changed (BR-07) | 409 `This request was decided by someone else` |

## Permissions

| Operation | Requester | Stage-1 reviewer | Second reviewer | Other user |
|---|---|---|---|---|
| Read the request | ✓ | ✓ | ✓ | 404 |
| Approve / reject in `SUBMITTED` | 403 | ✓ | – (not set yet) | 404 |
| Approve / reject in `SECOND_REVIEW` | 403 | 403 (D-37) | ✓ | 404 |
| See it in the Review queue | – | in `SUBMITTED` | in `SECOND_REVIEW` | – |

## API

| Method | Path | Change |
|---|---|---|
| POST | `/api/requests/:id/approve` | Response `status` can be `SECOND_REVIEW`; body gains `secondReviewer: UserRef \| null`. Errors add 403 (D-37) and 409 (D-36). |
| POST | `/api/requests/:id/reject` | Allowed in `SECOND_REVIEW` for the second reviewer. |
| GET | `/api/requests/:id` | Readable by the second reviewer; body gains `secondReviewer: UserRef \| null` and `needsSecondApproval: boolean`. |
| GET | `/api/reviews/queue` | `reviewerId = me AND status = SUBMITTED` **OR** `secondReviewerId = me AND status = SECOND_REVIEW`; items gain `stage: 1 \| 2`. F-08 filters are ANDed with this whole condition. |
| GET | `/api/requests/mine` | Unchanged; `status` may be `SECOND_REVIEW`. |

## Data

Migration `add_second_review`:
- `ALTER TYPE "RequestStatus" ADD VALUE 'SECOND_REVIEW'`.
- `secondReviewerId TEXT NULL REFERENCES "User"(id)`, index `(secondReviewerId, status)` for the queue.
- CHECK `"secondReviewerId" IS NULL OR ("secondReviewerId" <> "requesterId" AND "secondReviewerId" <> "reviewerId")`.
- CHECK `"secondReviewerId" IS NOT NULL OR status <> 'SECOND_REVIEW'` (a stage-2 request always has its reviewer).
- Existing rows: all `secondReviewerId = NULL`; no data change.

**Effects on existing code (to verify in the implementation):**
- `transitions.ts`: `SECOND_REVIEW: { APPROVE: "APPROVED", REJECT: "REJECTED" }`; the stage-1 approve target depends on the amount, so `decide.ts` picks `SECOND_REVIEW` when `requiresSecondApproval(amount)` (new helper next to `requiresApproveComment`).
- `decide.ts`: the scope query adds `{ secondReviewerId: reviewerId }` to the `OR`; the conditional update matches the acting reviewer column for the current stage.
- `assign-reviewer.ts`: reuse `pickReviewer` with the stage-1 reviewer removed from the list.
- `read.ts` `findReadableRequest`: `OR` adds `secondReviewerId`; F-05's nullable `reviewerId` is unaffected.
- Client: `RequestDetailPage` (who sees the Decision section), `DecisionSection` success text, `ReviewQueuePage` Stage column, types.

## Acceptance criteria

| ID | Given / When / Then |
|---|---|
| AC-07-1 | Given a request of exactly 50,000.00 THB, when the reviewer approves, then it is `APPROVED` in one step (Sprint 1 behavior kept). |
| AC-07-2 | Given 50,000.01 THB, when the stage-1 reviewer approves with a comment, then the status is `SECOND_REVIEW`, a second reviewer of the same department is set who is neither the requester nor the stage-1 reviewer, and one history row `SUBMITTED → SECOND_REVIEW` is written. |
| AC-07-3 | Given a `SECOND_REVIEW` request, then it is in the second reviewer's queue with stage 2 and no longer in the stage-1 reviewer's queue. |
| AC-07-4 | Given `SECOND_REVIEW`, when the second reviewer approves with a comment, then `APPROVED`; when they reject with a reason, then `REJECTED`; history then has Submitted → Approved (stage 1) → Approved/Rejected (stage 2). |
| AC-07-5 | Given `SECOND_REVIEW`, when the stage-1 reviewer decides, then 403; the requester 403; anyone else 404 with the unknown-id body; nothing changes. |
| AC-07-6 | Given no eligible second reviewer, when the stage-1 reviewer approves above D-02, then 409 D-36 and the request stays `SUBMITTED` without a new history row; reject still works. |
| AC-07-7 | Given two simultaneous stage-2 decisions, then exactly one is stored (BR-07). |
| AC-07-8 | Given stage 2, when approving without a comment, then 400 BR-08. |
| AC-07-9 | Given the UI: detail shows the two-approval note and the second reviewer; the Decision section shows only for the acting reviewer; a stage-1 approval shows the "Sent to …" message; the queue shows the Stage column. |
