# F-03: My requests (list and detail with history)

**Linked requirements:** FR-04, FR-07, NFR-03
**Depends on:** F-01 (`requireAuth`, `createUser`, `loginAs`), F-02 (`Request`, `RequestHistory`)
**Used by:** F-04b (the Approve and Reject buttons go on the detail page from this feature)
**Version history:** v1 (2026-11-12, Nantakorn) – initial

## Decisions

Proposed; to be accepted in the PR review.

| ID | Decision | Why |
|---|---|---|
| D-10 | A request is readable by its requester and by its assigned reviewer. Anyone else gets **404**, with the same body as for an id that does not exist. | NFR-03 allows 403 or 404. With 404, nobody can tell whether another user's request exists (SDS §5: "404 not found or not yours"). |
| D-11 | "My requests" lists the requests **I submitted**, newest first. A reviewer's assigned requests are not in it; they are in the F-04 queue. | FR-04 is about the requester's own requests; mixing in assigned work would make the list mean two things. |
| D-12 | No paging in Sprint 1: the list returns all of my requests. Filtering and paging come with F-08 (Sprint 2). | One user has a few dozen requests at most in Sprint 1. The response is wrapped in `{ "requests": [...] }` so paging fields can be added later without breaking the client. |

## Behavior and workflow

1. A signed-in user clicks "My requests" in the header and sees their requests: title, category, amount, status, submitted time, and reviewer.
2. Clicking a title opens the request's detail page: every field, the requester and reviewer, and the full history.
3. The history lists every entry oldest first: who did it, the action, the status change (`– → SUBMITTED` for the submit), the reason if any, and when.
4. After submitting in the F-02 form, the confirmation links to the new request's detail page.

## Business rules, validation, errors

| Case | Expected behavior |
|---|---|
| Not signed in (NFR-01) | 401 `UNAUTHENTICATED` on both endpoints |
| Requester opens their own request | 200 with the detail |
| Assigned reviewer opens the request | 200 with the detail |
| Any other user opens the request, including another reviewer in the same department (NFR-03, D-10) | 404 `NOT_FOUND`, `"Request not found"`, no request data |
| The id does not exist, or has the wrong format | 404 `NOT_FOUND`, `"Request not found"` (same body as above) |
| The user has no requests | 200 with `{ "requests": [] }` |
| History rows (BR-06) | Only read; F-03 never changes them |

## Permissions

- `GET /api/requests/mine`: any signed-in user. Only rows with `requesterId` = the signed-in user.
- `GET /api/requests/:id`: any signed-in user; the handler checks requester or assigned reviewer (D-10). The check is in the database query, so a request the user may not read is never loaded.

## UI

New pages: "My requests" at `/requests` and the request detail at `/requests/:id`. The header gets a "My requests" link.

| Page | State | Behavior |
|---|---|---|
| List | Loading | "Loading…" (`role="status"`) |
| List | Empty | "You have not submitted any requests yet." with a link to New request |
| List | Error | The API's message (`role="alert"`) |
| List | Loaded | A table: title (link to detail), category, amount (THB, 2 decimals), status, submitted, reviewer |
| Detail | Loading | "Loading…" (`role="status"`) |
| Detail | Not found (404) | "Request not found." and a link back to My requests |
| Detail | Error | The API's message (`role="alert"`) |
| Detail | Loaded | Title, status, category, amount, description, requester, reviewer, submitted time; a "History" list, oldest first |
| F-02 form | Success | The confirmation also links to the new request ("View request") |

A 401 on either page goes to the login page through the F-01 v2 handler in `api()`; the pages do not handle it.

## API

| Method | Path | Request | Success | Errors |
|---|---|---|---|---|
| GET | `/api/requests/mine` | – | 200, list body below | 401 |
| GET | `/api/requests/:id` | – | 200, detail body below | 401, 404 |

List, newest `submittedAt` first (ties: higher id first). No description or history, to keep it small:

```json
{
  "requests": [
    {
      "id": "<id>",
      "title": "Conference travel",
      "category": "TRAVEL",
      "amount": "1500.00",
      "status": "SUBMITTED",
      "submittedAt": "2026-11-12T09:00:00.000Z",
      "reviewer": { "id": "<id>", "email": "rev.eng1@example.com", "name": "Chai" }
    }
  ]
}
```

Detail: the F-02 response plus `name` on `requester` and `reviewer`, and `history`, oldest first (ties: lower id first):

```json
{
  "id": "<id>",
  "title": "Conference travel",
  "category": "TRAVEL",
  "amount": "1500.00",
  "description": "Train tickets to the conference",
  "status": "SUBMITTED",
  "submittedAt": "2026-11-12T09:00:00.000Z",
  "requester": { "id": "<id>", "email": "req.eng1@example.com", "name": "Anan" },
  "reviewer": { "id": "<id>", "email": "rev.eng1@example.com", "name": "Chai" },
  "history": [
    {
      "id": "<id>",
      "action": "SUBMIT",
      "fromStatus": null,
      "toStatus": "SUBMITTED",
      "reason": null,
      "createdAt": "2026-11-12T09:00:00.000Z",
      "actor": { "id": "<id>", "email": "req.eng1@example.com", "name": "Anan" }
    }
  ]
}
```

`/mine` is registered before `/:id`, so "mine" is never read as an id.

## Data

No change. The list uses the existing index on `Request.requesterId`, and the history uses `RequestHistory(requestId, createdAt)`.

## Acceptance criteria

| ID | Given / When / Then |
|---|---|
| AC-03-1 | Given requests from several users, when a user opens My requests, then only the requests they submitted are listed, newest first, each with status. |
| AC-03-2 | Given a user with no requests, when they open My requests, then the list is empty (API) and the empty message is shown (UI). |
| AC-03-3 | Given a request, when its requester or its assigned reviewer opens it, then the detail and the full history are shown. |
| AC-03-4 | Given another user's request, when someone who is neither its requester nor its assigned reviewer opens it, then the response is 404 with the same body as for an unknown id, and no request data. |
| AC-03-5 | Given several history entries, when the detail is opened, then all entries are shown oldest first with actor, action, from → to, reason, and time. |
| AC-03-6 | Given no session, when either endpoint is called, then the response is 401. |
| AC-03-7 | Given the pages, when loading, empty, not found, or an API error happens, then the matching state from the UI table is shown. |
