# F-02: Submit request with reviewer assignment

**Linked requirements:** FR-02, FR-03, FR-07, BR-04, BR-06, NFR-01
**Depends on:** F-01 (`User` model, `requireAuth`, `createUser`, `loginAs`)
**Version history:** v1 (2026-11-06, Nantakorn) – initial; v2 (2026-11-10, Nantakorn) – D-01, D-03, D-04 accepted in the PR #10 review; 400 body gains `details`; CHECK constraints added by hand to the migration; v3 (2026-11-11, Nantakorn) – history action values, tests T-02-18 to T-02-20; v4 (2026-11-12, Nantakorn) – form fields locked while submitting (PR #12 review), test T-02-21

## Decisions

Accepted by Member A in the PR #10 review (2026-11-06).

Because of D-01, the seed and the UAT accounts need at least 2 reviewers in every department that has requesters. Otherwise a department's only reviewer can never submit, and a department without reviewers cannot submit at all.

| ID | Decision | Why |
|---|---|---|
| D-01 | Round-robin among `REVIEWER` users in the requester's department, never the requester. No fallback to another department: if nobody is eligible, the submit fails with 409. | Spreads work evenly, and a reviewer from another department may not be entitled to see the request. |
| D-03 | `category` is one of `TRAVEL`, `SUPPLIES`, `EQUIPMENT`, `TRAINING`, `OTHER`. | The SRS names the field but no values. A fixed list keeps FR-11 filtering simple. |
| D-04 | `title` is required (1–200 characters) and `description` is required (1–2000 characters), both after trimming. | FR-02 lists both fields, and a reviewer needs the description to decide. |

## Behavior and workflow

1. A signed-in user opens "New request", fills in the form, and submits.
2. The API validates the body. On failure it returns 400 and stores nothing.
3. The API assigns a reviewer (see below).
4. In one transaction, the API inserts the `Request` with status `SUBMITTED` and `submittedAt = now`, and inserts the first `RequestHistory` row.
5. The client shows the created request's status and its assigned reviewer.

### Reviewer assignment

- Eligible reviewers: users with role `REVIEWER` in the requester's department, ordered by id, without the requester.
- "Last assigned": the reviewer of the most recently submitted request whose reviewer is in that department.
- The next reviewer is the first eligible one after "last assigned" in the ordered list, wrapping around to the start. With no previous request, it is the first eligible one.
- Two simultaneous submissions may get the same reviewer. This is accepted: it affects only how evenly work is shared, never a business rule.

## Business rules, validation, errors

| Case | Expected behavior |
|---|---|
| `amount` is not a JSON number (for example `"500"`) | 400 `VALIDATION_ERROR` |
| `amount` ≤ 0 (BR-04) | 400 `VALIDATION_ERROR` |
| `amount` > 100,000 (BR-04) | 400 `VALIDATION_ERROR` |
| `amount` is exactly 100,000 or 0.01 | Accepted |
| `amount` has more than 2 decimal places | 400 `VALIDATION_ERROR` |
| `title` or `description` is missing, blank, or too long | 400 `VALIDATION_ERROR` |
| `category` is missing or not in the list | 400 `VALIDATION_ERROR` |
| Several fields are invalid | One 400 whose `message` lists every problem and whose `details` has one entry per invalid field |
| Body contains `status`, `reviewerId`, `requesterId`, or `submittedAt` | Ignored; the server sets these values |
| No eligible reviewer in the department | 409 `CONFLICT`, nothing stored |
| Not signed in (NFR-01) | 401 `UNAUTHENTICATED`, nothing stored |
| Database failure during the transaction | 500 `INTERNAL_ERROR`; neither row is stored |

## Permissions

- `POST /api/requests`: any signed-in `REQUESTER` or `REVIEWER`. A reviewer's own request goes to a different reviewer.
- The requester is always the signed-in user, never a value from the body.
- Reading requests is F-03.

## UI

New "New request" page with title, category, amount, and description.

| State | Behavior |
|---|---|
| Invalid input | Message beside each invalid field; no API call |
| Submitting | Submit button and all fields disabled, so a double click cannot create two requests and no edit is lost when the form resets after success |
| Success | Confirmation with status `SUBMITTED` and the assigned reviewer |
| API error (400, 409, 500) | The API's `message` shown; the form keeps what the user typed |
| Not signed in | Login page (from F-01) |

## API

| Method | Path | Request | Success | Errors |
|---|---|---|---|---|
| POST | `/api/requests` | `{ "title": string, "category": string, "amount": number, "description": string }` | 201, body below | 400, 401, 409 |

```json
{
  "id": "<id>",
  "title": "Conference travel",
  "category": "TRAVEL",
  "amount": "1500.00",
  "description": "Train tickets to the conference",
  "status": "SUBMITTED",
  "submittedAt": "2026-11-06T09:00:00.000Z",
  "requester": { "id": "<id>", "email": "requester@example.com" },
  "reviewer": { "id": "<id>", "email": "reviewer@example.com" }
}
```

`amount` is returned as a string so the decimal value is exact. The `id` type follows the `User` model from F-01.

A 400 adds `details` to the usual error body, so the form can show each message beside its field (AC-02-9). `field` is one of `title`, `category`, `amount`, `description`. Other errors keep the plain `{ error, message }` body.

```json
{
  "error": "VALIDATION_ERROR",
  "message": "Title is required; Amount must be greater than 0",
  "details": [
    { "field": "title", "message": "Title is required" },
    { "field": "amount", "message": "Amount must be greater than 0" }
  ]
}
```

This needs an optional `details` on `HttpError` and `badRequest()` in `server/src/http.ts`. That change is part of the route work, and the error handler includes `details` only when it is set.

## Data

Migration `add_requests`, created after the F-01 migration is on `staging`. Prisma cannot express CHECK constraints in `schema.prisma`, so the migration is created with `npx prisma migrate dev --create-only --name add_requests`. The two CHECK constraints below are added to its `migration.sql` by hand before it is applied. An API + DB test checks that the database itself rejects a bad row, and does not rely only on validation.

| Table | Fields | Constraints |
|---|---|---|
| `Request` | id, requesterId, reviewerId, title, category, amount DECIMAL(12,2), description, status, submittedAt | Foreign keys to `User`; `CHECK (amount > 0 AND amount <= 100000)`; `CHECK (requesterId <> reviewerId)`; index on `(reviewerId, status)` |
| `RequestHistory` | id, requestId, actorId, fromStatus (null on submit), toStatus, action, reason (null on submit), createdAt | Foreign keys to `Request` and `User`; the application only inserts (BR-06) |

`status` is an enum with `SUBMITTED`, `APPROVED`, and `REJECTED`. `category` is an enum with the D-03 values. `RequestHistory.action` is an enum with `SUBMIT`, `APPROVE`, and `REJECT`; F-04 writes the last two, and later features add values with a migration.

The seed adds a few sample requests and stays safe to rerun.

## Acceptance criteria

| ID | Given / When / Then |
|---|---|
| AC-02-1 | Given a signed-in requester, when they submit valid data, then the response is 201, the request is stored with status `SUBMITTED`, and one history row records `null → SUBMITTED` by the requester. |
| AC-02-2 | Given an amount ≤ 0, > 100,000, not a number, or with more than 2 decimal places, when submitted, then the response is 400 and nothing is stored. Exactly 0.01 and 100,000 are accepted. |
| AC-02-3 | Given a missing or blank title, description, or category, or an unknown category, when submitted, then the response is 400 and nothing is stored. |
| AC-02-4 | Given no session, when submitting, then the response is 401 and nothing is stored. |
| AC-02-5 | Given any requester, including a reviewer submitting their own request, when a reviewer is assigned, then the reviewer is never the requester. |
| AC-02-6 | Given several reviewers in a department, when requests are submitted one after another, then they are assigned in turn. |
| AC-02-7 | Given no eligible reviewer in the department, when submitting, then the response is 409 and nothing is stored. |
| AC-02-8 | Given a body containing `status`, `reviewerId`, or `requesterId`, when submitted, then those values are ignored. |
| AC-02-9 | Given invalid form input, when the user submits, then field messages appear and no API call is made. Given an API error, the message appears and the input is kept. |
