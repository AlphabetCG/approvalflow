## Behavior and workflow

1. A reviewer opens the queue and sees the requests waiting for them.
2. They open one (F-03 detail page) and approve it, or reject it with a reason.
3. In one transaction the API changes the status and inserts one `RequestHistory` row (actor, action, from → to, reason).
4. The request leaves the queue. The requester sees the new status and the history entry in F-03.

### State machine (Sprint 1)

| From | Action | To |
|---|---|---|
| `SUBMITTED` | `APPROVE` | `APPROVED` |
| `SUBMITTED` | `REJECT` | `REJECTED` |

Every other combination is an invalid transition (BR-02): 409 and nothing changes.

### Simultaneous decisions (BR-07)

The status update is conditional: `UPDATE ... WHERE id = :id AND status = 'SUBMITTED' AND reviewerId = :me`. If two decisions arrive together, PostgreSQL lets only one update the row; the other updates 0 rows and gets 409. The history row is inserted in the same transaction, so a request never has two decision rows.

## Business rules, validation, errors

Checks run in this order, and the first failure decides the response:

| # | Case | Response |
|---|---|---|
| 1 | Not signed in | 401 `UNAUTHENTICATED` |
| 2 | Signed in, role is not `REVIEWER` | 403 `FORBIDDEN` |
| 3 | Reject: reason missing, not a string, or under 10 characters after trimming; any reason over 1000 characters; approve: comment not a string | 400 `VALIDATION_ERROR` with `details: [{ field: "reason", message }]` |
| 4 | Request does not exist, or the caller is neither its requester nor its reviewer | 404 `NOT_FOUND`, "Request not found" (same body for both) |
| 5 | The caller is the request's requester (a reviewer deciding on their own request) | 403 `FORBIDDEN`, "You cannot decide on your own request" (BR-01) |
| 6 | Status is not `SUBMITTED` | 409 `CONFLICT`, "This request is already APPROVED" / "REJECTED" (BR-02) |
| 7 | Another decision won the race | 409 `CONFLICT`, "This request was decided by someone else" (BR-07) |

In cases 1–7 the request and its history are unchanged.

## API

| Method | Path | Request | Success | Errors |
|---|---|---|---|---|
| GET | `/api/reviews/queue` | – | 200 `{ "requests": QueueItem[] }` | 401, 403 |
| POST | `/api/requests/:id/approve` | `{ "reason"?: string }` | 200 `Decision` | 400, 401, 403, 404, 409 |
| POST | `/api/requests/:id/reject` | `{ "reason": string }` | 200 `Decision` | 400, 401, 403, 404, 409 |

```json
// QueueItem
{
  "id": "<cuid>",
  "title": "Conference travel to Chiang Mai",
  "category": "TRAVEL",
  "amount": "4500.00",
  "submittedAt": "2026-11-12T08:00:00.000Z",
  "requester": { "id": "<cuid>", "email": "req.eng1@example.com", "name": "Anan" }
}

// Decision
{
  "id": "<request cuid>",
  "status": "REJECTED",
  "decision": {
    "id": "<history cuid>",
    "action": "REJECT",
    "fromStatus": "SUBMITTED",
    "toStatus": "REJECTED",
    "reason": "Please attach the receipt first.",
    "createdAt": "2026-11-12T09:00:00.000Z",
    "actor": { "id": "<cuid>", "email": "rev.eng1@example.com", "name": "Chai" }
  }
}
```

`decision` has the same shape as a `HistoryEntry` in F-03, so the client can append it to the detail page's history.

## Data

No migration. `RequestStatus` already has `APPROVED` and `REJECTED`, and `HistoryAction` already has `APPROVE` and `REJECT` (F-02 contract v3). The queue uses the index `(reviewerId, status)`.

## Acceptance criteria

| ID | Given / When / Then |
|---|---|
| AC-04-1 | Given a reviewer with assigned `SUBMITTED` requests, when they open the queue, then they see only those requests, oldest first, and no decided or someone else's requests. |
| AC-04-2 | Given the assigned reviewer, when they approve, then the response is 200, the status is `APPROVED`, and one history row records `SUBMITTED → APPROVED` by them (with the comment, if any). |
| AC-04-3 | Given the assigned reviewer, when they reject with a valid reason, then the response is 200, the status is `REJECTED`, and the history row holds the trimmed reason. |
| AC-04-4 | Given a reject with no reason, a blank reason, or one under 10 characters, or any reason over 1000 characters, then the response is 400 with `details` for `reason`, and nothing changes. |
| AC-04-5 | Given a reviewer who submitted a request (assigned to someone else), when they try to approve or reject it, then the response is 403 and nothing changes (BR-01). |
| AC-04-6 | Given a reviewer who is not assigned, or an unknown id, then the response is 404 with the same body, and nothing changes. |
| AC-04-7 | Given a user with role `REQUESTER`, when they call the queue, approve, or reject, then the response is 403. Without a session it is 401. |
| AC-04-8 | Given an `APPROVED` or `REJECTED` request, when the reviewer approves or rejects it again, then the response is 409 and no history row is added (BR-02). |
| AC-04-9 | Given two approvals of the same request at the same time, then exactly one succeeds, the other gets 409, and there is exactly one `APPROVE` history row (BR-07). |
