## Behavior and workflow

1. A reviewer opens the queue and sees the requests waiting for them.
2. They open one (F-03 detail page) and approve it, or reject it with a reason.
3. In one transaction the API changes the status and inserts one `RequestHistory` row (actor, action, from → to, reason).
4. The request leaves the queue. The requester sees the new status and the history entry in F-03.

### State machine (Sprint 1)

| From | Action | To |
|---|---|---|
| `SUBMITTED` | `APPROVE` | `APPROVED` |
| `SUBMITTED` | `REJECT` | `REJECTED` |

Every other combination is an invalid transition (BR-02): 409 and nothing changes.

### Simultaneous decisions (BR-07)

The status update is conditional: `UPDATE ... WHERE id = :id AND status = 'SUBMITTED' AND reviewerId = :me`. If two decisions arrive together, PostgreSQL lets only one update the row; the other updates 0 rows and gets 409. The history row is inserted in the same transaction, so a request never has two decision rows.

## Business rules, validation, errors

Checks run in this order, and the first failure decides the response:

| # | Case | Response |
|---|---|---|
| 1 | Not signed in | 401 `UNAUTHENTICATED` |
| 2 | Signed in, role is not `REVIEWER` | 403 `FORBIDDEN` |
| 3 | Reject: reason missing, not a string, or under 10 characters after trimming; any reason over 1000 characters; approve: comment not a string | 400 `VALIDATION_ERROR` with `details: [{ field: "reason", message }]` |
| 4 | Request does not exist, or the caller is neither its requester nor its reviewer | 404 `NOT_FOUND`, "Request not found" (same body for both) |
| 5 | The caller is the request's requester (a reviewer deciding on their own request) | 403 `FORBIDDEN`, "You cannot decide on your own request" (BR-01) |
| 6 | Status is not `SUBMITTED` | 409 `CONFLICT`, "This request is already APPROVED" / "REJECTED" (BR-02) |
| 7 | **(v4)** Approve, the request's amount is above 20,000.00, and the comment is missing, blank, or under 10 characters after trimming | 400 `VALIDATION_ERROR`, `details: [{ field: "reason", message: "Approving a request over 20,000 THB needs a comment of at least 10 characters" }]` (BR-08, D-17) |
| 8 | Another decision won the race | 409 `CONFLICT`, "This request was decided by someone else" (BR-07) |

In cases 1–8 the request and its history are unchanged. (v3 had cases 1–7; v4 inserts the new check 7 before the race, so the race is now 8.)

## API

| Method | Path | Request | Success | Errors |
|---|---|---|---|---|
| GET | `/api/reviews/queue` | – | 200 `{ "requests": QueueItem[] }` | 401, 403 |
| POST | `/api/requests/:id/approve` | `{ "reason"?: string }` | 200 `Decision` | 400, 401, 403, 404, 409 |
| POST | `/api/requests/:id/reject` | `{ "reason": string }` | 200 `Decision` | 400, 401, 403, 404, 409 |

```json
// QueueItem
{
  "id": "<cuid>",
  "title": "Conference travel to Chiang Mai",
  "category": "TRAVEL",
  "amount": "4500.00",
  "submittedAt": "2026-11-12T08:00:00.000Z",
  "requester": { "id": "<cuid>", "email": "req.eng1@example.com", "name": "Anan" }
}

// Decision
{
  "id": "<request cuid>",
  "status": "REJECTED",
  "decision": {
    "id": "<history cuid>",
    "action": "REJECT",
    "fromStatus": "SUBMITTED",
    "toStatus": "REJECTED",
    "reason": "Please attach the receipt first.",
    "createdAt": "2026-11-12T09:00:00.000Z",
    "actor": { "id": "<cuid>", "email": "rev.eng1@example.com", "name": "Chai" }
  }
}
```

`decision` has the same shape as a `HistoryEntry` in F-03, so the client can append it to the detail page's history.

## Data

No migration. `RequestStatus` already has `APPROVED` and `REJECTED`, and `HistoryAction` already has `APPROVE` and `REJECT` (F-02 contract v3). The queue uses the index `(reviewerId, status)`.

## UI (F-04b)

The header shows only the links the user's role can use: everyone gets "My requests" and "New request"; a `REVIEWER` also gets "Review queue". Hiding a link is not authorization; the API still enforces every rule.

| Screen / state | Behavior |
|---|---|
| Header, reviewer | "Review queue" link to `/reviews`; not shown to a requester |
| Queue, loading / error | "Loading…" (`role="status"`) / the API's message (`role="alert"`) |
| Queue, empty | "Nothing to review." |
| Queue, loaded | Table, oldest first: title (link to the F-03 detail page), requester, category, amount (THB), submitted |
| Detail page, assigned reviewer, `SUBMITTED` | A "Decision" section: one text field "Comment or reason" and two buttons, "Approve" and "Reject". The field is optional for approve and required for reject (10–1000 characters after trimming). **(v4)** If the amount is above 20,000.00 THB the field is also required for approve (10–1000), and the hint says so: "Required when approving a request over 20,000 THB and when rejecting (10–1000 characters)." Nobody else sees the section, and it is gone once the request is decided. |
| Invalid input (reject with fewer than 10 characters, anything over 1000; **v4:** approve above 20,000.00 with fewer than 10) | Message beside the field; no API call |
| Deciding | Field and both buttons disabled, so a double click sends one decision |
| Success | "Request approved." / "Request rejected." (`role="status"`); the status and the history update from the response, without reloading |
| 400 from the API | Its `details` message beside the field |
| 403 / 404 / 409 from the API | Its message (`role="alert"`); the page reloads the request, so it shows the current status (for example after someone else decided) |
| History entry | An approve comment is labelled "Comment:"; a reject reason "Reason:" |

One field instead of a separate reject dialog: a decision is final (D-16), and both buttons and the text they will send stay in view; a modal would add a step without adding information.

## Acceptance criteria

| ID | Given / When / Then |
|---|---|
| AC-04-1 | Given a reviewer with assigned `SUBMITTED` requests, when they open the queue, then they see only those requests, oldest first, and no decided or someone else's requests. |
| AC-04-2 | **(revised v4)** Given the assigned reviewer and a request of at most 20,000.00 THB, or any request with a valid comment (AC-04-13), when they approve, then the response is 200, the status is `APPROVED`, and one history row records `SUBMITTED → APPROVED` by them (with the comment, if any). |
| AC-04-3 | Given the assigned reviewer, when they reject with a valid reason, then the response is 200, the status is `REJECTED`, and the history row holds the trimmed reason. |
| AC-04-4 | Given a reject with no reason, a blank reason, or one under 10 characters, or any reason over 1000 characters, then the response is 400 with `details` for `reason`, and nothing changes. |
| AC-04-5 | Given a reviewer who submitted a request (assigned to someone else), when they try to approve or reject it, then the response is 403 and nothing changes (BR-01). |
| AC-04-6 | Given a reviewer who is not assigned, or an unknown id, then the response is 404 with the same body, and nothing changes. |
| AC-04-7 | Given a user with role `REQUESTER`, when they call the queue, approve, or reject, then the response is 403. Without a session it is 401. |
| AC-04-8 | Given an `APPROVED` or `REJECTED` request, when the reviewer approves or rejects it again, then the response is 409 and no history row is added (BR-02). |
| AC-04-9 | Given two approvals of the same request at the same time, then exactly one succeeds, the other gets 409, and there is exactly one `APPROVE` history row (BR-07). |
| AC-04-10 | Given a reviewer, the header shows "Review queue"; given a requester, it does not. The queue page shows loading, empty, error, and the assigned requests. |
| AC-04-11 | Given the assigned reviewer on a `SUBMITTED` request, the Decision section is shown; given anyone else, or a decided request, it is not. A reject with a reason under 10 characters shows a message and makes no API call; a 400 from the API shows its message beside the field. |
| AC-04-12 | Given a decision, when the API answers 200, then the page shows the new status and the new history entry; when it answers 409, then the message is shown and the page shows the current status. |
| AC-04-13 | **(v4)** Given the assigned reviewer and a `SUBMITTED` request above 20,000.00 THB, when they approve without a comment, with a blank comment, or with fewer than 10 characters after trimming, then the response is 400 with `details` for `reason` and the status and History do not change; with 10–1000 characters the approval succeeds and the History row holds the trimmed comment. At exactly 20,000.00 no comment is needed. |
| AC-04-14 | **(v4)** Given an unassigned reviewer or an unknown id, a request above 20,000.00 approved without a comment still gets 404 with the same body (D-13); a decided request still gets 409; nothing changes. |
| AC-04-15 | **(v4)** Given the assigned reviewer on a request above 20,000.00 THB, the hint says a comment is required to approve; approve with an empty or too-short comment shows "Approving a request over 20,000 THB needs a comment of at least 10 characters" beside the field and sends no request. At 20,000.00, approve without a comment still sends `{}` to `/approve`. |
