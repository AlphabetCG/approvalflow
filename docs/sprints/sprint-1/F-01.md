## Decisions

Accepted by Member B in the PR #11 review (2026-11-11).

| ID | Decision | Why |
|---|---|---|
| D-05 | Server-side sessions stored in the database, identified by an HttpOnly cookie. No JWT. | Logout takes effect at once, and sessions survive a redeploy or a second Cloud Run instance (Lab 5). |
| D-06 | A session lasts 8 hours from login (absolute, not extended by activity). `SESSION_TTL_HOURS` changes it. | One working day; simple to test. |
| D-07 | Emails are case-insensitive: stored and compared in lower case, trimmed. | `Alice@Example.com` and `alice@example.com` are the same person. |
| D-08 | User ids are strings (`cuid`). | Ids in URLs cannot be guessed by counting; F-02 orders reviewers by id. |
| D-09 | Sprint 1 roles: `REQUESTER`, `REVIEWER`. `ADMIN` is added in Sprint 2 with its own migration. | Keeps Sprint 1 to the two roles the theme requires. |

## Behavior and workflow

1. A user who is not signed in sees the login page for every screen.
2. They enter email and password. The API checks them and, on success, creates a session and sets the session cookie.
3. The client loads `GET /api/auth/me` and shows the user's name and role in the header.
4. Logout deletes the session in the database and clears the cookie. The client returns to the login page.

### Session lifecycle

- **Create:** on successful login. The server generates 32 random bytes (base64url) as the token and stores only its SHA-256 hash, with `expiresAt = now + 8 h`. A database leak therefore does not expose usable tokens.
- **Use:** every request reads the cookie, hashes the token and looks it up. A missing, unknown, or expired session counts as signed out. An expired session row is deleted when it is found, and the response clears the stale cookie so later requests skip the lookup.
- **End:** logout deletes the row. Logging in again creates a new session, and older sessions stay valid until they expire or are logged out.
- **Cleanup:** every successful login deletes all expired session rows, so sessions abandoned without logout do not pile up.
- **Cookie:** name `af_session`, `HttpOnly`, `SameSite=Lax`, `Path=/`, `Max-Age` equal to the session length, and `Secure` when `NODE_ENV=production`. `SameSite=Lax` together with JSON-only endpoints is the CSRF protection for Sprint 1.

### Passwords

- Stored only as bcrypt hashes (cost 12). Plain passwords are never logged, returned, or stored.
- Unknown email and wrong password give the same 401 and run a bcrypt comparison either way, so neither the response nor its timing reveals which emails exist.
- Accounts come from the seed only. Self-registration and password reset are out of scope (SRS Section 3).

## Business rules, validation, errors

| Case | Expected behavior |
|---|---|
| `email` or `password` missing, empty, or not a string | 400 `VALIDATION_ERROR` |
| Unknown email, or wrong password | 401 `INVALID_CREDENTIALS`, message "Email or password is incorrect", no cookie set |
| Email in different case or with spaces around it | Treated as the same email |
| `/api/auth/me` without a cookie, or with an unknown or expired session | 401 `UNAUTHENTICATED` |
| Logout without a session | 204 (logout is idempotent) |
| Signed-in user calls an operation their role may not use | 403 `FORBIDDEN` |
| Not signed in, on any protected operation | 401 `UNAUTHENTICATED`, and no protected data in the body |

## Permissions

| Operation | Who |
|---|---|
| `POST /api/auth/login` | Anyone |
| `POST /api/auth/logout` | Anyone (does nothing without a session) |
| `GET /api/auth/me` | Signed-in users |

Middleware for the other features:

- `requireAuth`: 401 unless signed in; otherwise sets `req.user = { id, email, name, role, department }`.
- `requireRole(...roles)`: 401 unless signed in; 403 unless `req.user.role` is one of `roles`.

## UI

| Screen / state | Behavior |
|---|---|
| Any screen, not signed in | Login page |
| Login page | Email and password fields, "Sign in" button |
| Submitting | Button disabled |
| Login failed (401) | "Email or password is incorrect"; email kept, password cleared |
| API unreachable, or it answers 5xx | "Cannot reach the server. Try again." |
| Signed in | Header shows name and role, and a "Sign out" button |
| Sign out | Back to the login page |
| Sign out fails (network error or 5xx) | Stay signed in, because the session may still be valid; header shows "Sign out failed. Try again." |
| Any API call except login answers 401 (session expired or deleted) | Back to the login page with "Your session has ended. Please sign in again." Pages do not handle 401 themselves. |

## API

| Method | Path | Request | Success | Errors |
|---|---|---|---|---|
| POST | `/api/auth/login` | `{ "email": string, "password": string }` | 200 `{ "user": User }` and `Set-Cookie: af_session=...` | 400, 401 |
| POST | `/api/auth/logout` | – | 204 and the cookie cleared | – |
| GET | `/api/auth/me` | – | 200 `{ "user": User }` | 401 |

```json
{ "user": { "id": "<cuid>", "email": "alice@example.com", "name": "Alice", "role": "REQUESTER", "department": "ENGINEERING" } }
```

`passwordHash` and session data never appear in a response.

## Data

Migration `add_auth`.

| Table | Fields | Constraints |
|---|---|---|
| `User` | id (cuid), email, name, passwordHash, role, department, createdAt | email unique (stored lower case); role enum `REQUESTER`, `REVIEWER` |
| `Session` | id (SHA-256 hex of the token), userId, expiresAt, createdAt | FK to `User`, delete with the user; index on `userId` |

`department` is a free string in Sprint 1. The seed uses `ENGINEERING` and `FINANCE`.

## Seed

- Demo users per department, with at least 2 reviewers in each (needed by D-01 in F-02):
  - `ENGINEERING`: 2 requesters, 2 reviewers
  - `FINANCE`: 1 requester, 2 reviewers
- All demo users get the password from `DEMO_USER_PASSWORD`. Without it, the seed skips the users and says so, so it never falls back to a password written in code. A value shorter than 8 characters is refused.
- Rerunning the seed keeps existing users and their passwords (upsert by email).
- Emails use `example.com`. The password is shared with the Lab 6 partner team privately, never in the repository.

## Acceptance criteria

| ID | Given / When / Then |
|---|---|
| AC-01-1 | Given a seeded user, when they log in with the right email and password, then the response is 200 with their user (no `passwordHash`), an `af_session` cookie is set, and `/me` returns the same user. |
| AC-01-2 | Given a wrong password or an unknown email, when logging in, then both give the same 401 `INVALID_CREDENTIALS` body and no cookie. |
| AC-01-3 | Given a missing, empty, or non-string email or password, when logging in, then the response is 400. |
| AC-01-4 | Given no cookie, an unknown token, or an expired session, when calling `/me`, then the response is 401. |
| AC-01-5 | Given a signed-in user, when they log out, then the response is 204, their session row is deleted, and `/me` with the old cookie gives 401. |
| AC-01-6 | Given a route protected by `requireRole("REVIEWER")`, then a requester gets 403, a reviewer gets through, and an anonymous caller gets 401. |
| AC-01-7 | Given a seeded or created user, then the database holds a bcrypt hash, not the password, and no session row contains the cookie token. |
| AC-01-8 | Given a user `alice@example.com`, when logging in as ` Alice@Example.COM `, then login succeeds. |
| AC-01-9 | Given the client, when not signed in, the login page is shown; a failed login shows the error and keeps the email; a successful login shows the name and role; sign out returns to the login page. |
| AC-01-10 | Given `DEMO_USER_PASSWORD`, when the seed runs twice, then the demo users exist once each. Without it, no users are created. |
| AC-01-11 | Given a signed-in user, when sign out fails, then they stay signed in and see "Sign out failed. Try again.", with no unhandled error. |
| AC-01-12 | Given the login API answers 5xx or cannot be reached, then the form shows "Cannot reach the server. Try again." |
| AC-01-13 | Given a signed-in user on any page, when an API call (other than login) answers 401, then the login page appears with "Your session has ended. Please sign in again." |
| AC-01-14 | Given expired sessions in the database, when anyone logs in, then the expired rows are deleted; given a request with an unknown or expired cookie, then the response clears that cookie. |
