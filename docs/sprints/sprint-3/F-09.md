## Decisions

Proposed here; accepted in the review of this contract (recorded in `docs/srs.md` §7).

| ID | Decision | Why |
|---|---|---|
| D-39 | One endpoint **`GET /api/reviews/summary?from=&to=`**, role `REVIEWER` only. It summarizes **the caller's own decisions**; there is no parameter to pick another reviewer. | FR-12 says "reviewers can see a summary of decisions". Their own decisions keep NFR-03 simple: no new access rule. A department or admin view is Sprint 3+ work (Admin role). |
| D-40 | A decision is a `RequestHistory` row with `actorId = me` and action `APPROVE`, `REJECT` or (F-06) `RETURN`. `SUBMIT`, `CREATE_DRAFT`, `RESUBMIT` are not decisions. Each row counts once: with F-07 a stage-1 and a stage-2 approval are two decisions of two reviewers. | History is append-only (BR-06) and already records every decision with its actor and time, so no new table is needed and the numbers can be checked against the detail pages. |
| D-41 | `from` / `to` filter on the **decision time** (`RequestHistory.createdAt`), as inclusive Asia/Bangkok days with the F-08 rules (D-26, D-28): same parser, same messages, `from` after `to` = 400, repeated = 400, empty = no limit. No dates = all time. | Same date meaning and code as the list filters; "decisions this month" is about when the reviewer decided, not when the request was submitted. |
| D-42 | Response: `{ "from": "2026-11-01" \| null, "to": "2026-11-30" \| null, "approved": n, "rejected": n, "returned": n, "total": n, "approvedAmount": "123456.78" }`. `returned` is `0` until F-06 exists. `approvedAmount` is the sum of the request amounts over my `APPROVE` rows, summed as Decimal on the server, sent as a string with 2 decimals (like every amount, F-03). | A fixed shape the client can show without checking which features exist. Decimal avoids float sums of money. |

**Out of scope for F-09:** charts, CSV export, grouping by category or month, other reviewers' or department totals, average decision time.

## Behavior and workflow

1. A reviewer opens **My decisions** (`/reviews/summary`, a nav link next to Review queue, shown for reviewers only).
2. The page reads `from` / `to` from its URL and calls `/api/reviews/summary` with them; without dates it shows all time.
3. The API validates the dates (F-08 parser, `allowStatus: false`, only `from`/`to` read), counts the caller's decision rows in the range by action and sums the amounts of the approved requests.
4. The page shows four numbers (Approved, Rejected, Returned, Total) and "Amount approved: 123,456.78 THB", with the range as text ("All time" or "1 Nov 2026 – 30 Nov 2026").
5. From / To inputs and **Apply** / **Clear** change the URL (same behavior as the F-08 filter bar, including "To must not be before From" on the client).

### Check order

| # | Check | Response |
|---|---|---|
| 1 | No session (NFR-01) | 401 |
| 2 | Role is not `REVIEWER` | 403 `FORBIDDEN` |
| 3 | Bad `from` / `to` (D-41) | 400 `VALIDATION_ERROR` with `details` |
| 4 | Valid | 200 summary (zeros when there are no decisions) |

## Permissions

| Operation | Requester | Reviewer | No session |
|---|---|---|---|
| See my decision summary | 403 | ✓ (own decisions only) | 401 |

Parameters such as `reviewerId` or `actorId` are ignored (D-28), so a reviewer can never see another reviewer's numbers.

## UI

| Place | Behavior |
|---|---|
| Nav | "My decisions" link for reviewers only (the API still answers 403 to requesters). |
| Page | Heading "My decisions"; range text; a `<dl>` with Approved, Rejected, Returned, Total; "Amount approved" formatted with `formatAmount` + " THB". |
| Date bar | From, To, Apply, Clear; values from the URL on load; From after To → message beside To, no call. |
| Loading / errors | "Loading…"; a 400 shows its `details` messages in an alert; other errors the API message. |

## API

| Method | Path | Query | Success | Errors |
|---|---|---|---|---|
| GET | `/api/reviews/summary` | `from`, `to` (optional, YYYY-MM-DD, Bangkok) | 200 D-42 body | 400, 401, 403 |

Example: `GET /api/reviews/summary?from=2026-11-01&to=2026-11-30`

```json
{ "from": "2026-11-01", "to": "2026-11-30", "approved": 3, "rejected": 1, "returned": 0, "total": 4, "approvedAmount": "45000.50" }
```

## Data

No migration. Reads `RequestHistory` (`actorId`, `action`, `createdAt`) joined to `Request.amount`. One query per call with `findMany` on history rows of the caller in the range (`where: { actorId, action: { in: [...] }, createdAt: { gte, lt } }`, `select: { action, request: { select: { amount } } }`) and the counting and Decimal sum in TypeScript; a reviewer has at most a few hundred decisions. New index `@@index([actorId, createdAt])` on `RequestHistory` is **not** added in this sprint (noted as a scaling item).

**Effects on existing code (to verify in the implementation):**
- New `server/src/reviews/summary.ts`: `summarizeDecisions(reviewerId, range)` and the pure `tally(rows)` (unit-tested).
- `server/src/requests/filters.ts` (F-08): reuse `parseRequestFilters` for `from`/`to`; the summary ignores `status`/`category` (they are not read, like unknown parameters).
- `routes/reviews.ts`: `GET /summary` with `requireRole("REVIEWER")`.
- `DECISION_ACTIONS` is computed from the `HistoryAction` enum (`APPROVE`, `REJECT`, plus `RETURN` when F-06 adds it), so F-06 needs no change here.
- Client: `reviews/DecisionSummaryPage.tsx`, route `/reviews/summary`, nav link; the date part of `FilterBar` reused (`withStatus={false}`, no category: a `withCategory` prop).

## Acceptance criteria

| ID | Given / When / Then |
|---|---|
| AC-09-1 | Given a reviewer with 2 approvals and 1 rejection, when they open the summary without dates, then approved 2, rejected 1, returned 0, total 3, and `approvedAmount` is the exact sum of the two approved amounts. |
| AC-09-2 | Given another reviewer's decisions and the reviewer's own submit rows, then they are never counted (D-39, D-40). |
| AC-09-3 | Given decisions at 2026-11-09 23:59:59.999, 2026-11-10 00:00:00.000, 2026-11-20 23:59:59.999 and 2026-11-21 00:00:00.000 Bangkok time, when `from=2026-11-10&to=2026-11-20`, then only the middle two are counted. |
| AC-09-4 | Given bad dates (as F-08 T-08-06), then 400 with `details`. |
| AC-09-5 | Given no session, then 401; given a requester, then 403. |
| AC-09-6 | Given no decisions, then all counts are 0 and `approvedAmount` is `"0.00"`. |
| AC-09-7 | Given amounts 0.10 and 0.20 approved, then `approvedAmount` is `"0.30"` (Decimal, no float error). |
| AC-09-8 | Given the UI: the counts and amount are shown; the dates from the URL are used; Apply / Clear change the URL; From after To shows the message without a call; a 400 shows its messages; requesters have no nav link. |
